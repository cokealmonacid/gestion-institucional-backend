# Acervo platform administration specification

## Laravel operator panel (2026-10-15)

The functional interface is served by this backend at **`/platform`** (local entry: **`http://127.0.0.1:8000/platform`**). It uses a public, stateless Blade shell, a dedicated Vite/Alpine entry point and the existing same-origin `/api/v1/platform` APIs. Spanish forms, tables, native keyboard-accessible confirmation dialogs and escaped text rendering cover operator authentication, institutions, onboarding, catalog plans, immediate immutable agreement amendments, administrator invitations/repair and filterable audit history. No dashboard charts, document access or impersonation are provided.

Authentication never uses institutional cookies or the institutional Axios client. Fetch omits credentials, cache and referrers; the platform Bearer, password-first challenge, setup secret, email proof and one-time recovery codes exist only in memory. There is no administrative view before a completed MFA login and profile verification. Reload requires fresh login/MFA; expiry, logout and page exit clear client authentication and loaded administrative data. Recovery-code consumption leads to restricted MFA reenrollment, never an administrative token. TOTP setup uses the manual key (6 digits, 30 seconds); no QR dependency or external service is used. Password change revokes sessions; code regeneration invalidates previous codes and shows the replacement once.

Actual platform email destinations remain `/platform/activate` and `/platform/password-reset`. The platform-only builder now carries `email` and `token` in the **URL fragment**, which browsers do not send to HTTP access logs. The shell reads and immediately removes that fragment before assets load. Previously issued query-string links remain accepted and are scrubbed too; operators of an HTTP proxy must suppress/redact query strings for these legacy paths, since browser code cannot remove an already received request from upstream logs. The response has `no-store`, `no-referrer`, frame denial and a same-origin CSP. No analytics or third-party assets are loaded. Institutional email builders/destinations are unchanged.

Creation review freezes the payload and a UUID idempotency key **before the request**. Only that safe draft (customer/admin metadata, conditions, original operator ID, key and safe result identifiers) is kept in `sessionStorage`, never credentials or access links. Storage must be writable before submission. An uncertain operation survives reload/reauthentication in the same tab and is shown only after the original operator signs in. Lookup 404 does not authorize a new key; the UI offers lookup or identical-key/payload replay. A different creation is blocked while an outcome is unresolved. Confirmed/rejected administrator invitations clear pending state automatically and return to the editable form; confirmed resources stay visible even when publication fails. Onboarding retains its result until explicitly closed. Closing the entire tab removes browser session storage and is discouraged while an operation is unresolved.

Operational and commercial revisions remain server-authoritative. On a stale revision the panel keeps safe inputs and requires an explicit current-state refresh and another review. Agreement review shows exceptions and resulting quota excess without deleting existing users. Catalog updates never rewrite existing agreements. Invitation UI labels account creation, queue publication, transport acceptance and activation separately; transport acceptance is never described as delivery. All mutations block duplicate submission; errors distinguish validation, permissions, suspension, conflicts, throttling and uncertain outcomes without printing raw exceptions.

The metadata-only administrator directory, `GET /api/v1/platform/institutions/{id}/administrators` (`q`, `page`, `per_page`), uses the existing `platform.administrator_access` permission and MFA Bearer middleware, including for suspended institutions, and excludes deleted/non-admin/foreign users. Its closed rows expose only user ID, name, email, active/activation state and access revision. Canonical platform administration is **3.3.0**; platform authentication is **1.1.0** and institutional contracts are unchanged.

Main navigation now includes **Usuarios**. `GET /api/v1/platform/users` uses the same administrator-access permission and MFA boundary; server-side filters are `q`, `institution_id`, `role` (`admin`, `editor`, `reader`, `none`), `active` (`true`/`false`), `page` and `per_page` (1–100). Explicit resources include institution identity, all actual role memberships (including no roles), activity, email verification and a nullable authoritative invitation summary. Email verification alone is not proof of invitation consumption. Soft-deleted users and platform operators are excluded. Opening an administrator reuses existing institution-scoped access/actions; other users have only the explicit containment/email-correction actions described below, without general editing. Invitations require explicit institution selection and use existing quota/permission rules. No promotion, transfer, impersonation, deletion or general user editing is added.

The optional `user_id` UUID filter retrieves a current access summary within the selected institution. Opening or refreshing a user rechecks its current memberships and metadata; a stale directory row does not determine which actions appear.

Invitation correction: `409 EMAIL_UNAVAILABLE` is a definitive rejection with transaction rollback, distinct from `409 IDEMPOTENCY_CONFLICT`. The email field retains its value and offers correction; the rejected operation no longer blocks the form. A confirmed invitation clears pending state and refreshes the administrator list, quota usage and access summary, even when publication failed. For network/unknown outcomes or an idempotency conflict, retain the exact key/payload: use operation lookup or explicit identical-key replay. Lookup 404 alone never permits a new key. Access summaries group account and invitation status; generation/access revision are collapsed technical details. Read-only refresh requires no reason; mutations retain their existing reason requirements.

To resolve a previously rejected invitation manually: return to its result and use **Corregir invitación** (or close a definitively rejected legacy draft), then search **Usuarios** for the email and inspect its institution and roles. New-account invitations cannot reuse an existing institutional email, including inactive/deleted records. Use an existing eligible administrator's access summary for an explicit authorized resend/reactivation; another role or institution does not authorize promotion/transfer. Correct the email only for a genuinely new account and review the new request. An unresolved operation must first be reconciled with its original key; do not discard it based on missing lookup alone.

Access-link publication and the platform portion of the preflight origin check use this same policy; the institutional URL still requires HTTPS. ### Implemented block B boundary

Block B adds no onboarding or new platform administrator invitation endpoint. It implements computed role quotas, last-usable-admin protection, operational suspension/reactivation and scoped existing-administrator status/resend/reactivation. Canonical platform administration is now **2.0.0** because enforcement and the closed revision resource changed; platform authentication remains **1.0.0**. The seven affected institutional contracts use the major versions in section 9 (the actual explorer baseline was 5.1.0, now 6.0.0). Nothing was published remotely.

`InstitutionalAccess`, `MembershipPolicy` and `InstitutionUserMutations` are the shared tenant boundary. Every quota admission uses locking current reads of users and pivots under the institution lock, including multi-role accounts and active pending/expired invitations. Shared role definitions use shared rather than exclusive locks. Limits come from the current immutable agreement revision, irrespective of commercial dates/lifecycle; legacy institutions remain unlimited. No usage counters are stored. Explicit published role replacement still replaces memberships and preserves responsibility-impact confirmation/rollback; edits without a role preserve every existing membership. Initial pending-admin and zero-usable-admin states are not automatically promoted or activated.

Suspension and reactivation require reason/expected operational revision, increment institution epoch and atomically invalidate tokens, database sessions, remember credentials, invitation generations/hashes and recovery rows with audit. Both transitions preserve individual activity, documents, passwords/verification and commercial conditions. User access_revision also invalidates residual non-database sessions after access changes. Legacy credentials or sessions without epoch/revision metadata require fresh login; remember-cookie restoration without a stamped session also requires fresh login. Logout remains cleanup-capable. Mail publication and streamed responses do not hold tenant locks. Upload staging stays outside the tenant transaction and denial/rollback compensates the file. An admitted stream or in-progress provider send may finish; revoked links cannot activate/reset afterward.

All protected institutional API routes and authenticated web routes use the operational boundary. DB-only compatibility mutations are serialized by middleware before controller/resource locks; membership/mail actions and version uploads own their explicit transaction so no publication/staging happens under that middleware lock. Domain mutation actions recheck fresh actor permission under lock. Responsibility assignment locks its candidate user before its document. No frontend or storage quota changes were made.

Existing-administrator status is platform-only and available during suspension; resend/reactivation require enabled status. Reactivation checks expected_user_revision and every existing destination role quota, preserves roles/password/verification and never implicitly promotes. Resend rotates a reserved-seat invitation, audits before publication and returns recoverable failed/unknown publication status. New administrator creation/idempotency and onboarding operation lookup remain C.

Remaining release requirements: block C atomic onboarding/new administrator invitation/idempotency/status/preflight/reconciliation, coordinated frontend adoption, communicated credential cutover, PHP 8.4/MySQL/deployment session/queue verification and execution of guarded concurrency tests. The runtime public institution list and legacy password POST are retained until cutover. The legacy web dashboard still references the disabled profile route; no frontend repair was included. B alone is not production readiness.

Hidden credential fields; no institution_id or tenant role pivot. |
| `platform_access_links` | Operator, purpose activation/password_reset, token hash, generation, expiry, consumed/revoked timestamps and publication state. Tokens are distinct from institutional tokens and cannot authorize administrative APIs. |

Append-only. |
| `administrative_events` | UUID, actor_kind (platform/institutional/operator_cli/migration), actor ID and safe identity snapshot, action, subject kind/ID, institution ID when relevant, allowlisted before/after JSON, reason, UTC timestamp, operation/request ID. No cascading deletion of history. |
| `platform_operations` | Unique operator+operation_type+idempotency_key, canonical request fingerprint, resulting resource IDs and safe creation response, committed timestamp. Retain for the resource lifetime; no automatic key reuse. |

Finite maxima are integers 0..2147483647; all three fields must be present and null alone means unlimited. No usage column. Keep pivot memberships intact. Subject/actor deletion must retain IDs and snapshots, using restricted deletion or nullable live references rather than cascade deletion. Application append-only protection is not a claim of tamper-proof storage against privileged SQL. Database accounts should lack unnecessary update/delete privileges on history where operationally feasible.

Customer fields are institution-owned metadata, not a shared CRM customer table. Multiple institutions may carry the same RUT. Do not add a RUT unique constraint or deduplicate by institution name. For a natural person, customer_name is the person's name; for a legal entity, its legal name. Customer identity remains optional for a free trial; `agreement_kind=paid` requires type, nonblank name and valid RUT even if its negotiated price is zero. A free trial must have price zero and trial/pilot dates. Record complete customer identity in each paid contract snapshot; later metadata corrections do not rewrite earlier revisions.

RUT processing: accept digit body, optional thousands separators, a hyphen/check digit and surrounding whitespace; reject other characters. Remove formatting, normalize leading zeros in the numeric body and uppercase K; canonical storage/output is digits-hyphen-check digit. Validate positive body (at most eight digits), calculate standard modulo-11 check digit, map 10 to K and 11 to 0. Put parsing/checksum in one value object shared by all requests; synthetic fixtures must cover valid numeric/K cases and invalid checksums. Validation is syntactic and does not establish taxpayer ownership or legal status.

## 3. Agreed conditions and time semantics

Use a complete snapshot for every revision. Catalog edits/withdrawal only affect future selections. A source plan must be available when creating a new agreement or explicitly switching plans; amendments retaining the already-contracted plan remain permitted after withdrawal. Require expected_plan_revision when reading catalog defaults into a contract; reject stale selections. Plan edits require expected_revision.

For an amendment retaining the same plan_id, preserve the existing source-plan revision, name/description and base-limit snapshot; expected_plan_revision must match that saved source revision, not today's catalog revision. Compare exceptions to that preserved baseline. Selecting a different plan explicitly takes its current available catalog snapshot under lock. Refreshing defaults from a changed version of the same catalog plan is deferred; an operator can record changed negotiated limits as exceptions without rewriting the source snapshot.

Contract body: agreement_kind, lifecycle, plan_id, expected_plan_revision, limits, price_clp, currency, tax_treatment (`inclusive`/`exclusive`), periodicity (`monthly`/`annual`/`one_time_pilot`), starts_on, ends_on, trial (nullable), exceptions, reason. Every condition is explicit; price is a nonnegative whole-peso decimal string, stored as a lossless decimal string in the immutable JSON snapshot, never float or a duplicate price column. No automatic price proration, tax or renewal billing. `one_time_pilot` requires pilot dates; monthly/annual do not generate invoices.

Each exception has condition from a closed list, base_value, agreed_value and nonblank reason. Role-limit deviations from plan defaults require one matching exception per changed role. Price/date/periodicity negotiations may carry exceptions with base_value=null where the catalog supplies no corresponding baseline. Duplicate conditions and contradictions with final values are 422 errors. General revision reason is also mandatory.

All business dates use YYYY-MM-DD in America/Santiago. starts_on is inclusive; optional ends_on is inclusive through that local day, operationally equivalent to an exclusive next-local-midnight bound. Calculate using timezone-aware calendar days, not fixed 24-hour offsets. Trial/pilot dates are inclusive, end required and not before start; must lie inside contract validity where an end exists. Timestamps are UTC RFC3339. Capture server time once for each committed mutation.

Revision effectiveness is immediate at the successful transaction: no scheduled or backdated revision activation in this increment. effective_at is server-owned; current_revision_id is authority and revision number breaks equal-timestamp ambiguity. Contract starts_on may be future or historical commercial metadata; it does not defer quota enforcement. Derived validity is not_started/current/expired, independent of lifecycle and operational status. A terminated/expired agreement retains its last agreed limits until an explicit revision replaces them. Trial expiry never selects another limit, starts billing or suspends access. This avoids needing a scheduler and makes quota conditions deterministic.

Existing institutions without agreements remain legacy_unconfigured with unlimited limits. New onboarding always creates a configured agreement. No endpoint changes a configured institution back to legacy_unconfigured. Lowering any quota below usage succeeds and reports excess without changing users.

## 4. Authorization and operator MFA

| Principal | Platform administration/audit | Institution APIs/content/history | Access lifecycle |
| --- | --- | --- | --- |
| Anonymous | Denied | Denied; retire public institution listing | Public credential/link/challenge endpoints only, rate limited |
| Password-verified operator, MFA pending | Denied | Denied | Only purpose-bound MFA enrollment/challenge; logout/cancel |
| Active operator with completed MFA and current platform token | Allowed according to explicit platform permission | Always denied, including reads/search/history and web session paths | Own password/MFA lifecycle and scoped administrator intervention |
| Institutional admin/editor/reader/roleless user | Always denied | Existing Gates plus principal/activity/status/epoch checks | Existing institutional lifecycle; users.manage remains admin only |
| Operations CLI | Explicit bootstrap/reissue/MFA recovery actions only | No implicit content access | Audited operator recovery/provisioning |

Create distinct platform token authentication that accepts only Bearer tokens with a PlatformOperator tokenable; do not fall back to institutional web cookies. Existing institutional middleware must reject every non-User principal before typed Gates/controllers/resources. Never install a universal Gate bypass. Platform abilities do not appear in institutional profile resources. Same email in the two identity stores is permitted because endpoints/providers/token purposes remain separate.

MFA dependency: maintained OTPHP stable 11.5.0 is installed and locked. Its [declared requirements](https://github.com/Spomky-Labs/otphp/blob/11.5.0/composer.json) permit PHP >=8.1 without a Laravel dependency. The [maintainer release history](https://github.com/Spomky-Labs/otphp/releases) identifies the two provisioning-URI security fixes in 11.4.3, included in 11.5.0. Composer resolution and tests succeeded on PHP 8.5.4; PHP 8.4 runtime is assigned to CI, not claimed as locally tested. Acervo generates its own provisioning URI and never imports third-party URIs. Composer audit reports no advisories for either newly added package, but reports 38 advisories across 11 pre-existing packages; no baseline dependency versions were upgraded in block A.

Alternative assessed: [Fortify requirements](https://raw.githubusercontent.com/laravel/fortify/1.x/composer.json) include Laravel 13 and PHP ^8.2. Its [login pipeline](https://raw.githubusercontent.com/laravel/fortify/1.x/src/Actions/RedirectIfTwoFactorAuthenticatable.php) and [MFA trait](https://raw.githubusercontent.com/laravel/fortify/1.x/src/TwoFactorAuthenticatable.php) would require adapting session challenges, identity/provider integration and recovery-code storage to these Bearer endpoints and hashed codes. OTPHP is recommended to avoid that authentication-framework expansion. Acervo still owns lifecycle orchestration and atomic replay state; it must not implement the TOTP algorithm or encryption itself.

Fixed MFA behavior:

1. CLI-provisioned activation sets password and verified_at, but issues no administrative session. Password login creates a 5-minute opaque enrollment challenge when MFA is absent, or a login challenge when enrolled. Issuing a replacement challenge invalidates earlier challenges for that operator/purpose. Maximum five verification failures per challenge; expiry or exhaustion requires fresh password verification.
2. Enrollment generates the secret through the library. Store pending/confirmed secrets using Laravel authenticated encryption in TEXT fields, never in audit or logs. Return an Acervo issuer provisioning URI/manual secret only to the enrollment challenge with Cache-Control: no-store; no third-party QR service. A backend QR dependency is unnecessary: the eventual client may render the URI locally. Expired enrollment discards pending secret.
3. Confirmation verifies six-digit TOTP, SHA-1, 30-second periods, at most the current step and adjacent +/-1 steps. Use the library verifier at explicit candidate timestamps and record the greatest matching step. Confirmation atomically promotes the secret, records that step, generates ten high-entropy recovery codes through Laravel secure randomness, stores individual password hashes and consumes the challenge. Return codes once, then require a fresh password login/challenge before issuing an admin token. Lost confirmation responses require CLI recovery; plaintext codes are not stored for replay.
4. Login verification locks operator then challenge; require current epoch/active/verified/MFA state. Accept a matched TOTP step strictly greater than last_accepted_step; update it and consume challenge in the same transaction as audit and token issuance. Replay protection is global per operator/secret, including concurrent challenges, not local process/cache state.
5. A recovery code requires a password-verified challenge and is consumed under operator/code locks. Successful recovery revokes existing tokens/challenges, increments auth_epoch and returns only a reenrollment challenge, not administrative access. Reenrollment replaces secret/codes; MFA never becomes optional.
6. Regenerating recovery codes requires a current platform token, current password and a fresh unused TOTP. Replace hashes atomically, show plaintext once, audit only the event/count. No disable-MFA endpoint, trusted-device cookie or configurable policy.
7. Password recovery uses platform-specific single-use links. Reset updates only password/auth_epoch and revokes tokens/challenges; it preserves confirmed MFA and recovery codes. Next login still requires MFA. A password reset cannot become an enrollment bypass. Authenticated password change has the same revocation behavior.
8. Lost authenticator and exhausted codes require an operations CLI recovery workflow, a recorded incident/reason, explicit operator identity verification outside the app and an accountable OS operator identity. It revokes credentials for access, resets MFA to enrollment_required, invalidates codes/challenges and issues a short-lived recovery link. Never issue an admin token or reveal a TOTP secret. No platform API performs this override.

Fixed rate limits: password login five/minute per normalized email+IP and 20/minute per IP; verification/enrollment five/minute per operator+IP plus persisted five-attempt challenge limit and 20/minute per IP; recovery request one/minute per email plus five/minute per IP; reset/activation five/minute per link subject+IP. Shared limiter storage is required across instances; database challenge attempts/replay state remain authoritative. Rate-limit failed and successful attempts; 429 includes Retry-After. Platform access tokens expire after 60 minutes, store mfa_verified_at and auth_epoch in token metadata, and require completed MFA/current epoch on every request. No refresh token. Synchronize server clocks; no widening of the drift window as a workaround.

## 5. Quotas, usable administrators and locking

For role r, usage(r) is the number of distinct user IDs with institution_id matching, active=true, deleted_at=null and an actual role_user membership whose role type is r. Pending/expired invitation status does not alter occupancy. Multi-role users count once per assigned role. Roleless and multi-role users appear in integrity warnings; do not normalize their roles automatically or infer occupancy from the list's displayed first role.

Admission rule: calculate before/after membership contribution for the target. For every role whose contribution increases, reject if its finite limit would be exceeded. Non-increasing roles do not block an operation, even when already over quota. A same-role active no-op is allowed. Reactivating a multi-role user checks every added role. Combined role/activity changes evaluate final state. Inactive creation is not offered by the public legacy endpoint; new users are active. Inactive role edits remain permitted but still apply responsibility-impact semantics.

Allowed while over quota: profile-only edits, deactivation/deletion subject to last-admin protection, same-role no-ops, inactive-role edits, moves to a role with capacity, reserved-seat invitation resend/activation, login/recovery/document work in an enabled institution, and admissions in other roles with capacity. Rejected: any positive occupancy increase exceeding that role's limit. No hidden platform override; administrator repair that needs capacity requires an explicit audited quota revision.

A usable admin is active, non-deleted, email_verified_at not null, password not null, and carrying actual admin membership. Pending invitations never qualify. Under the same institution lock, reject a mutation if usable-admin count was >=1 and its final result is zero: delete, deactivate, demote or combined update, regardless of whether actor equals target. This intentionally replaces the old inactive-peer self-demotion rule. Account deactivation/deletion revokes target sessions/tokens and access links. Deactivation alone keeps document responsibilities; role loss still requires impact confirmation/removals, including zero affected documents.

If usable count is already zero (new onboarding or legacy damage), allow repair and otherwise valid mutations that do not remove a usable admin; expose usable_admin_missing. Platform can invite a new administrator, inspect/resend invitations or reactivate an existing admin. Reactivating an unverified admin reserves seats but does not repair the usable count until activation. Platform cannot grant admin to an existing non-admin through this endpoint, demote roles or inspect affected document identities. Initial onboarding requires capacity for its first pending admin. A quota of zero may be recorded below existing usage; it does not automatically remove the last admin. Suspension remains allowed regardless of usable-admin count.

Transaction protocol, implemented once in domain actions:

1. Lock institution by PK before membership, contract, status or last-admin decisions; reload actor from database and authorize current roles/activity/status/epoch. Platform mutations also recheck current operator access with a compatible lock order.
2. Read current contract pointer/revision with locking current reads. Lock institution user rows in UUID order (including inactive/soft-deleted target where needed), then their role_user rows in stable ID order. Use SELECT row columns ... FOR UPDATE and compute distinct contributions from those rows; do not use a stale aggregate snapshot or assume COUNT ... FOR UPDATE locks membership predicates. Role definitions are initialized once and not mutable through APIs.
3. Evaluate quota and usable-admin invariants against those current rows. Newly inserting users/pivots cannot race because all cooperating writers acquire the institution lock first. Add users(institution_id, deleted_at, active, id) and appropriate membership indexes, checking existing index redundancy.
4. For eligibility loss, lock affected active/inactive documents deterministically; validate existing role-impact token and confirmation, then write user/roles, responsibility changes/history/events and administrative audit atomically. Preserve rollback on history/event failure. Quota failure produces no document side effect.
5. Retry database deadlocks at most three times around database-only work. No mail, file publication or secret-return side effect inside a retried transaction.

Use current locking reads even if an earlier consistent read established a MySQL REPEATABLE READ snapshot. All HTTP/CLI membership writers must participate, including legacy POST, invites, PATCH, delete, platform admin interventions and activation. Institutional tenant transfer/restore is not exposed; future implementations must adopt the protocol. Factories and fixtures are test-only; production bootstrap must not call general seeders. Demo loaders must remain explicitly scoped to demo identity, never accept real customer targets or claim quota enforcement.

## 6. Operational suspension and access revocation

Enabled -> suspended and suspended -> enabled require reason and expected operational_revision. Lock institution; check revision; update status/revision, increment auth_epoch on each actual transition and append audit atomically. Same-state request with current revision is a no-op; stale revision is 409. Neither transition alters per-user/document/node active flags, agreements or commercial dates.

Suspension transaction invalidates every institutional invitation (clear token hash, advance generation, revoked_at/reason), password reset link and Sanctum token; rotates remember tokens and deletes identifiable database sessions. Record invalidation explicitly rather than pretending links were consumed. Introduce access epoch on issued institutional tokens and server-side web session data; middleware compares to institution epoch. Remember-me login must obey enabled status and epochs. Non-database session stores must have an equivalent epoch adapter; choose database sessions for the initial supported deployment. Reactivation never restores old tokens/links/cookies and requires fresh login/issuance.

Apply principal, user-active, operational-status and epoch checks to every protected API/web route, including profile/search/tags/document notes/history/downloads and runtime compatibility paths. Web login applies the same verification/activity/status rules. Keep disabled registration/password/profile/institution web mutation routes disabled. Logout only needs a recognizable principal/session and may clear local session state even when access is suspended/inactive; revoked Bearer tokens may receive 401, which clients treat as already logged out.

Institutional login locks institution before issuing a token, then reloads user eligibility. Every mutation rechecks status under institution lock, including document/node/tag legacy actions and password changes; middleware alone is insufficient. Acquire institution before existing document/version/node locks to prevent inversion. Role responsibility assignment follows the same order. For reads/downloads recheck immediately before response emission; do not hold a tenant lock for a streamed file's lifetime.

Version upload may stage its file outside the transaction, but must obtain institution lock/check before DB persistence and compensate the staged file on denial/rollback. Preserve current private storage and best-effort orphan cleanup behavior. No storage quota is added.

Recovery-request responses remain generic 202 and generate no job while suspended; reset/activation return generic link-unavailable errors. Mail workers check current eligibility/generation/epoch before transport. A previously admitted stream may finish; provider-accepted email cannot be recalled, and a send already in progress may complete after suspension. Its link must nevertheless be unusable. Do not hold DB locks across mail network calls.

## 7. Atomic onboarding and publication recovery

POST institution accepts exactly institution metadata, customer metadata, initial_admin {name,email}, and complete contract. Initial role is server-owned admin, active is true, password is null, institution is enabled and commercial state configured. Require Idempotency-Key (UUID) and expected_plan_revision; reject unknown nested properties. Normalize email consistently before preflight and insertion; the global institutional unique-email constraint remains final authority, including soft-deleted accounts.

In one transaction: verify operator access; acquire/create the uniquely scoped platform operation; compare canonical normalized request fingerprint; lock/check selected catalog plan revision; create institution, contract/revision, admin, role membership, hashed invitation and administrative events; persist resulting resource IDs and creation result. Missing role, invalid agreement, duplicate email or audit failure rolls everything back. Store idempotency response only with the committed mutation. Race on unique operation key must reload the winner; same payload replays 201 with Idempotency-Replayed: true, different payload returns IDEMPOTENCY_CONFLICT. No second admin or mail is created on replay. Every invocation still requires current platform authorization.

Dispatch mail explicitly AFTER the transaction has returned. Separate persistence exceptions from publication/post-commit exceptions. Committed resources must never be reported as rolled back. Return 201 with institution_id, contract_revision, initial_admin_id, invitation_id, activation_status=pending_activation, delivery_status, publication_status (`queued`/`failed`/`unknown`) and status/resend links. A transport exception, queue exception, or failure to refresh/mark the publication result must not convert a committed onboarding into generic creation 500. Use the saved safe IDs/result; failed diagnostic persistence leaves publication_status=unknown and a safe operational alert.

For this increment choose explicit resend and stale-pending reconciliation rather than a new outbox. Detect pending publication older than five minutes as publication_unknown in invitation status (derived, no false delivered claim). A crash between commit and dispatch is recoverable by querying the operation/resource and resending with a new token generation. The raw token is never durably stored except inside the encrypted queued job; a reconciler must not recover it from the hash. No automatic eventual-publication guarantee. Late jobs cannot update newer generations. Queues are at-least-once: duplicate email for the same generation remains possible. accepted means transport acceptance, not delivery.

Initial-admin resend and additional admin invitation require an enabled institution and quotas. Existing-admin reactivation requires actual admin membership; it never sets email_verified_at, password or roles. Status endpoints remain readable by MFA-verified operators during suspension; resending is denied until reactivation. Every successful access mutation has transactional audit; background publication outcomes append separate safe operational events when possible and cannot undo committed onboarding.

### Critical scenario walkthrough and replacement recommendation

With one technically usable departed admin and limit 1: invitation checks fail on a positive admin-seat delta; removal/deactivation through the tenant path fails the last-admin guard (and requires an available institutional principal); platform reactivation has no useful effect on an already active account; resend rejects an already verified account; password recovery cannot restore an inaccessible mailbox. No platform endpoint/CLI completes replacement. The test suite covers these individual guards, not a successful end-to-end replacement. This is a missing workflow, not evidence that quota or tenant isolation should be bypassed.

| Alternative | What it can do today | Why it is insufficient / recommended use |
| --- | --- | --- |
| Existing reachable second administrator | Can use tenant APIs to correct roles/activity within quota and last-admin rules. | Good ordinary path, but absent in the critical case. A stored second account is not proof of a reachable authorized person. |
| Invite and activate successor, then remove outgoing | Admission works only with capacity; a reachable tenant admin could later retire outgoing. | Platform cannot finish retirement. Increasing limits creates commercial changes and still leaves old access; do not prescribe it as a recovery workaround. |
| Deactivate outgoing first, then invite | Existing sole-admin guard blocks it; platform lacks deactivation. | Simply disabling the guard creates a lockout if admission/mail/activation fails. A targeted security freeze may intentionally lock out, but must be labeled containment, not restored continuity. |
| Change departed person's email / recover their password | No supported platform workflow. | Reusing their identity would blur actor history and is not an acceptable substitute for a new person's identity. Verified email change is for the same person only. |
| Suspend, reactivate, then recover | Suspension contains access but blocks current recovery writes; reopening retains passwords. | Useful immediate broad containment only; no supported end-to-end repair. |
| **Proposed prepared successor + atomic handover** | Not implemented. | Best fit for sole-admin/full-quota continuity; no permanent quota override or contract rewrite required. |

Recommended default: one MFA-authenticated Acervo operator records the institution's externally verified authority/request reference, reason, outgoing identity and named successor. Confirm both the representative's authority and successor's control of their own verified address; neither an old `email_verified_at` nor a new mailbox alone establishes authority. Use an existing same-institution identity or a new globally unique institutional email. No cross-institution transfer or platform-identity reuse.

For a new/unready successor, introduce a purpose-bound, expiring recovery-preparation proof with no tenant login/administrative access and no active-seat reservation. This is a proposed state/protocol: existing invitations require an active account and enabled institution and cannot supply it unchanged. Let the person establish their own password/address proof; never disclose/set a reusable password for them. A ready existing account still needs confirmation that its owner is the intended authorized successor. Keep outgoing access unchanged during ordinary preparation; freeze/suspend first if compromise is suspected. Failures/expiry before finalization leave the prior roster intact or the explicit containment incident unresolved, never falsely "recovered".

At explicit final confirmation, a single idempotent transaction revalidates operator authority, institution/user revisions, successor proof/eligibility and all memberships under the existing institution-first lock order. It enables/adds the successor's admin membership and disables outgoing access together. Validate **final net occupancy for every role**: a one-for-one admin replacement at capacity, or with pre-existing excess, is allowed if excess does not worsen; genuinely increasing another constrained role remains blocked. Assert a technical usable successor at commit; a pending ordinary invitation is insufficient. Keep the contract limits unchanged. Do not compose the current per-user `check` calls in an order that temporarily fails either quota or last-admin rules.

Revoke outgoing tokens, persisted sessions, remember credentials, reset proofs and invitation generations atomically; revoke/refresh successor credentials as needed for changed memberships so old sessions do not silently gain access. Persist safe before/after state, human authority reference and one correlated administrative operation result; publish any notifications only after commit, with honest failed/unknown outcomes and explicit resend. Default outgoing deactivation preserves historical identity and document responsibilities. Any optional eligibility-removing demotion needs a fresh impact token/count, explicit confirmation and atomic document/history changes with truthful platform attribution. Reversing a mistaken handover is a new verified operation; do not resurrect revoked proofs or rewrite history. A suspended institution stays suspended through preparation/finalization; restoring service is a separate explicit decision.

**High-value next:** ordinary scoped access correction/reactivation for other roles, eligibility-changing admin demotion after proper actor attribution, same-plan revision adoption, coordinated closeout UI, resumable operation lookup, attention worklists, plan/customer usage views, safe audit filters/export and external payment visibility. The already agreed institutional admin-role frontend increment consumes the shared membership/impact/revocation core; it is not implementation scope for this assessment.

Failed-mail automatic retries/outbox improvements are optional; an honest explicit recovery workflow is adequate initially.

Four cohesive increments avoid a project per finding:

1. **Institutional recovery core + small platform recovery UI (high complexity):** authority/proof preparation, containment and atomic handover, purpose-bound email correction, final-state quota evaluation and durable operation receipt. Dependency: safe platform actor attribution before eligibility-removing document changes; deactivation-only handover can preserve responsibilities initially. Include concurrent last-seat/activation/freeze/replacement tests, audit/history failure rollback and mail-after-commit uncertainty tests. Ordinary user mutations must share policies, not borrow an institutional identity for support.
2. **Operator lifecycle CLI (low–medium complexity):** inventory, freeze/offboarding, controlled reactivation and lost-email recovery, building on existing MFA/epoch/CLI accountability. Can proceed independently; provides a supported emergency path before wider production use.
3. **Commercial exception/closeout completion (medium complexity):** explicit same-plan snapshot adoption, coherent termination/suspension review and retention checklist; preserves immediate revision semantics. Depends on product closeout policy, not payment integration.
4. **Actionable support visibility (medium complexity):** attention lists, resumable scoped operation lookup, actor/date/operation audit filters, metadata export and plan/customer linkage views. Reuse existing authoritative quota/publication/contract facts; represent reported control loss explicitly rather than inferring it from account flags. Product-owner decisions still needed (defaults recommended):

- **Authority evidence:** accept a single operator's recorded verification against an established institutional representative plus request/ticket reference. Simple and accountable; a mailbox-only rule is weaker, mandatory multi-person approval adds delay without an identified need.
- **Handover disposition:** disable the outgoing identity and preserve historical roles/responsibilities initially. This avoids accidental history/assignment changes; eligible membership removal or reassignment remains a separately confirmed tenant/support action.
- **Emergency lockout:** allow targeted sole-admin containment with a visible unresolved recovery incident; prefer a deliberate temporary lockout to continued compromise. Ordinary replacement must still commit a usable successor atomically.
- **Service end:** default to explicit commercial termination plus confirmed operational suspension; agree retention/customer-delivery handling before irreversible disposal. No automatic expiry/payment suspension and no platform document browsing are proposed.
- **Payment visibility:** keep `untracked` until an authoritative external/manual source is chosen. A provenance-backed reference/status is useful before considering a payment integration; do not infer payment from the contract price or lifecycle.

No previously agreed identity, tenant, frontend increment or immutable-history decision is reopened by these proposals.

## Implemented institutional continuity and access control (2026-10-15)

This section supersedes the assessment's institutional replacement/containment/email-correction gaps, not its unrelated recommendations. Canonical administration is now **3.3.0**, platform authentication **1.1.0**. The new named permission is `platform.access_recovery`; existing gates grant it to the same MFA-authenticated, active, verified operator population. No operator lifecycle, commercial, general role-editing, demotion, document access/reassignment, payment or multi-institution capability was added.

Approved authority controls are implemented as required requester, institutional relationship, verification channel/reference, reason and explicit confirmation. Address possession is verified separately and never establishes institutional authority by itself. One accountable operator can prepare/complete recovery; no evidence uploads or multi-approver process. Another authorized operator can inspect and resume a durable operation without impersonating its creator or an institutional user.

### Supported operations and state

`POST /api/v1/platform/access-recoveries` requires a UUID `Idempotency-Key`, `kind`, institution/target IDs, expected target access revision and institution operational revision, authority, reason and confirmation. Its durable ID is that key. Identical original-operator/key/canonical-payload retries return the existing operation; conflicting reuse returns `IDEMPOTENCY_CONFLICT`. Lookup/listing is available to all operators with the recovery permission through `GET access-recoveries/{id}` and paginated `GET access-recoveries` (institution/target filters). This is a dedicated lifecycle table because preparation, verification and finalization are separate durable states; it reuses the existing client's frozen-request/idempotency pattern without changing ordinary invitation semantics.

- **Replacement:** select an eligible existing same-institution successor (`successor_id`) or provide a new person's own name/email (`successor_name`, `successor_email`). An existing successor must already have a verified address and password; inactive existing accounts are permitted if final quotas allow their full activation. Preparation does not change their password, activity, roles, sessions or legitimate access. A new successor has no institutional account/active seat until completion; their purpose-specific proof lets them establish their own password hash in the preparation, never a session. Platform identities remain separate; an institutional email cannot be reused across institutions, inactive/deleted users or live recovery reservations.
- **Containment:** `kind=containment` immediately and atomically disables one institutional account and revokes credentials with its audit/receipt. It deliberately bypasses only the platform containment path's last-admin restriction; ordinary institutional last-admin protection is unchanged. The result reports whether no technically usable administrator remains, and the UI links directly to replacement for an admin-role target. Already-inactive containment is explicit in the result; role memberships and document responsibilities remain unchanged.
- **Same-person email correction:** `kind=email_correction`, `new_email`, and `same_person=true` prepare a proof to the proposed address, retaining the current address until completion. No password, activity, membership, institution or person transfer occurs. Uniqueness is checked at preparation and again on finalization, including soft-deleted users and pending normalized-address reservations. A corrected active account in an enabled institution can subsequently use the existing institutional `/olvide-mi-contrasena` page (`POST /api/v1/auth/password-recovery`). This operation never sends that password-recovery request automatically; an inactive account or suspended institution remains ineligible.

Proofs expire after **one hour**, are purpose-bound to the operation/generation, stored only as hashes, and consumed once by public, rate-limited `POST /api/v1/platform/auth/access-recovery-verification`. Only a new successor may submit a new password; existing identities cannot reset their password through this proof. Verification changes `awaiting_verification` to `verified` with an audit category `address_proof`, explicitly describing mailbox control rather than an institutional or CLI identity. No user account or session is created by verification. Password hashes prepared for a new person are hidden and removed on cancellation/completion. Expired proofs cannot verify/finalize; expired email reservations are released on subsequent preparation or explicit cancellation.

An authorized operator explicitly calls `POST access-recoveries/{id}/complete`, `/cancel` or `/resend` with the current operation revision and confirmation. Cancel/resend also require a reason. Resend is throttled for 60 seconds, rotates the proof/generation, clears prior verification/prepared setup, and does **not** extend the original deadline. Cancel invalidates setup and releases the reservation without changing the institutional account; expired operations can still be cancelled. Completed/cancelled states cannot be repurposed. Completion/cancellation replay returns the existing terminal result rather than applying the transition again.

Completion locks the current operator, institution, operation and affected users consistently; rechecks current MFA/permission, proof/state/expiry, target and successor access/role/activity/email state, institution operational revision and agreement revision. Stale state returns `RECOVERY_STALE`; it does not silently rebase consent. The operator must inspect, cancel the known preparation and explicitly prepare again from current state. Changed commercial conditions are not bypassed just because the successor verified an older request.

Replacement evaluates **final occupancy for every actual role** using the shared membership policy. Final excess must not increase for any role. A one-for-one replacement works at a full administrator quota or with pre-existing excess, without editing limits. Activating an inactive successor's other roles can still be blocked if their excess would increase. An already-inactive outgoing administrator releases no additional seat; admitting another successor must still satisfy that final-state rule. The successor is enabled and receives the admin membership while retaining unrelated memberships; the outgoing account is deactivated. Its identity, roles, history and document responsibilities are preserved. No temporary zero-admin state or quota override is committed. Concurrent preparations for the same outgoing state cannot both complete; replay of the same completed operation returns its receipt.

The outgoing account and transitioned successor have tokens, persisted sessions, remembered credentials, reset links and ordinary invitation proofs revoked through `InstitutionalAccess::revoke`. Existing successor passwords are unchanged. Email correction revokes old-email reset/session/invitation credentials before changing the address and verifies the new address using the consumed proof; it preserves the password and activity. No flow logs a person in. Recovery preparation, verification and completion work while the institution is suspended and never change its operational status/authentication epoch. Tenant activation/login/recovery remain blocked until a separately confirmed institution reactivation.

Required state changes, administrative audit and recoverable result commit together; required audit failure rolls them back. Platform mutations retain the actual platform operator actor; mailbox proof uses the distinct `address_proof` category. No fabricated institutional actor or document-history writer change is needed because neither roles nor responsibilities are removed. Proof publication occurs only after the owning transaction commits, including nested transactions. Encrypted queue jobs check operation state, generation, proof hash and expiry; obsolete/cancelled jobs do nothing. Publication failure leaves the preparation discoverable. `queued` and `accepted` describe queue/transport acceptance, never delivery or verification; stale pending publication is displayed as unknown.
