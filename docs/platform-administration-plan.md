## 2. Block A: platform identity/MFA, plans, contracted conditions and audit

### A1. Identity boundary and dependency feasibility

Create `PlatformOperator` as a separate Authenticatable with Sanctum tokens. Add a platform-only Bearer authenticator; reject cookie fallback and non-platform tokenables. Add institutional principal middleware before existing typed Gates/controllers. No global authorization bypass, no changes to institutional RoleType. Existing institutional auth/profile resources continue to require a User and institution.

Introduce `PlatformPermission` and platform authorization definitions for metadata/plans/contracts/admin-access/audit. Initially all active, MFA-verified operators have the defined operator permission set; no configurable permission-management product is needed. Middleware reloads operator access/MFA/token epoch on every request; actions revalidate access at transactional mutation time.

Selected dependency: `spomky-labs/otphp` stable 11.5.0 is resolved, installed and pinned in composer.lock; the proposed 11.6.x line was development-only. It supplies TOTP/secret generation/provisioning URI; Laravel supplies encryption, hashing and secure randomness. No QR server dependency, SMS, paid service or Fortify registration/reset routes were added. Local resolver/runtime evidence is PHP 8.5.4; CI verifies PHP 8.4. Public-source release/security checks and injected-clock integration tests are complete. Keep future upgrades maintained and audited.

### A2. Platform MFA lifecycle and bootstrap

Implement activation/recovery links, password-first challenges, mandatory enrollment confirmation, TOTP login verification and single-use hashed recovery codes. Follow the exact purposes, lifetimes, attempt limits and replay rules in the specification. Token minting requires confirmed MFA and current operator epoch. Recovery codes issue restricted reenrollment, not an admin session. Password reset preserves MFA. Recovery without factors is operations-only CLI with reason/identity-verification runbook.

Use database operator/challenge/code locks for authoritative attempts and consumption; shared rate limiter for distributed request limits. Implement fixed TOTP verification window with library calls at candidate timestamps and persist accepted step. Do not build the OTP algorithm, encryption primitive or custom password hashing. Use server-controlled issuer/algorithm/period/digits; do not parse user-supplied provisioning URIs.

Add an audited, idempotent first-operator bootstrap with singleton marker; subsequent operator provisioning/reissue/recovery remains CLI-only. Hide all secrets, prevent public registration, and set no-store headers on enrollment/code responses. Return neither password nor raw access links from CLI. Separate platform reset/link storage from existing email-keyed institutional password reset table.

### A3. Commercial model and audit

Add catalog plan, institutional contract/revision, customer metadata, RUT value object, quota-limit value object and append-only administrative events. Implement CLP whole-peso decimal strings, explicit tax treatment, monthly/annual/one-time-pilot periods, inclusive Santiago dates and immediate revision pointer semantics. No scheduler for future terms, no payment/tax calculation. Snapshot complete agreed conditions and customer identity; amendments require expected revision/reason and exception validation.

Implement enabled plan selection with expected catalog revision. Withdrawing or editing a plan cannot touch contract snapshots. Lock institution for every contract update even before quota enforcement is activated. Legacy institutions remain unconfigured/unlimited; no invented agreements.

Create platform plan/contract/metadata/audit endpoints with safe resources and strict nested allowlists. Do not expose institution creation until C. Audit append failure aborts associated mutations. Preserve history independently of live actors/subjects. Use separate administrative events from document events; platform audit contains no document IDs/titles/content/history.

### A acceptance gate

- Anonymous, institution principal and pre-MFA operator are denied administrative endpoints.
- Completed platform sessions cannot use institution API or web/session routes.
- No token before MFA confirmation/challenge, no MFA bypass through recovery/reset, no TOTP/recovery-code reuse under concurrency.
- Plan revision/withdrawal preserves contracts; paid identity/CLP/dates/tax/exception validation works; RUT repetition across spaces is allowed.
- Invalid/stale contract mutation or audit failure leaves no partial writes.
- Bootstrap creates exactly one initial operator under concurrent attempts and supports recoverable publication/reissue without logging secrets.

## 3. Block B: quotas and consistent suspension across existing flows

### B1. One institutional membership mutation boundary

Extract legacy store, invitation admission, user update/delete and platform admin invite/reactivate into actions using a shared institution lock/context. Persist only validated DTO fields. Reject attempts to update password/verification/email/tenant/soft-delete/epoch through institutional PATCH. Legacy password POST retains its published shape until coordinated removal but becomes transactional, active-by-default and quota-aware.

Implement locking current-read usage by selecting actual user/pivot rows under the institution lock, then computing distinct role counts. Preserve multiple roles; do not use a displayed primary role, persisted counter, stale aggregate or COUNT-lock assumption. Apply positive-delta rules to combined activity/role mutations. Quota updates lock the same institution and report excess without changing memberships.

Replace old self-only demotion guard with last-usable-admin invariant across delete/deactivate/demote, including actor != target and combined changes. An activated verified active admin with password counts; inactive or invited admin does not. Allow repair when existing count is zero. No implicit quota bypass for platform repair; explicit condition revision precedes an admission requiring capacity.

Preserve RoleChangeImpact tokens, zero-document confirmation, stale detection, actual multi-role eligibility, active/inactive document removals, histories/revisions/events and atomic rollback. Profile-only/deactivation behavior must not remove responsibilities. Test quota/last-admin errors before confirming that no document side effect occurred.

### B2. Consistent operational access

Add operational_revision/auth_epoch checks, suspension/reactivation action and credential invalidation. Remove invitation tokens/advance generations/record revocation; invalidate password reset rows; revoke Sanctum tokens and database sessions; rotate remember tokens. Epoch compares on API/web requests and authentication issuance protect against unsupported residual credentials. Legacy tokens without epoch require communicated cutover logout; never assume restoring access can restore credentials.

Cover API login/logout/profile/password/search, invitation activation/resend, recovery issue/consume/jobs, every institution/node/tag/document/version/history/note route and runtime compatibility routes. Web login becomes eligibility-aware; disabled web mutation/registration routes remain disabled. Permit logout/local cleanup without operational access. Review route inventory against canonical documents and runtime-only registry.

Refactor every tenant mutation to acquire institution before resource locks and recheck status/current actor. Keep upload staging outside the tenant transaction, then check status before DB insertion and preserve compensating file deletion. Never retry network/file sends inside database deadlock retries. Reads and downloads recheck before response emission without holding a lock for the full stream. Document already-in-flight limitations.

Add narrowly scoped platform administrator status/resend/reactivation operations. Existing non-admin cannot be promoted through reactivation. Pending reactivation does not count as repaired usable-admin state; account activation does. Platform operators never receive document impact lists.
